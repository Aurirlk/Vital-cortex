### 0.2 本次实机复核得到的**新结论**（与既有报告不同之处）

1. **🔴 后端在任何 profile 下都无法启动**（比既有报告的判断更严重）。
   - 实跑 3 次，均为 `APPLICATION FAILED TO START: A component required a bean named 'dataSource' that could not be found.`
   - 根因：`config/Nl2SqlReadOnlyDataSourceConfig.java:41,65` 注册了一个 `DataSource` bean。
     Spring Boot 的 `DataSourceAutoConfiguration` 带 `@ConditionalOnMissingBean(DataSource.class)`，
     一旦容器里已存在任何 `DataSource` bean 定义就**整体退避**，主 `dataSource` 永不创建，
     随后 `DataAgentPipeline.java:90` / `JdbcSchemaIntrospector.java:46` 的 `@Resource(name="dataSource")` 装配失败。
   - 该类 `:41` 的条件 `@ConditionalOnProperty(prefix="crm.ai.nl2sql.read-only", name="url")`
     **对空字符串同样判定为"存在"**，因此 `application.yml:124` 的 `url: ${NL2SQL_RO_URL:}`（默认空）
     也会命中 → **不是"配了才炸"，是恒炸**。已实测：显式把 url 置空仍打印
     `[NL2SQL] 已启用只读数据源`，随后启动失败。
   - 该类 javadoc `:27-38` 自称 2026-10-07 已修复此问题——**修复只在 url 完全不存在时有效**，
     而 url 存在（哪怕为空）才是常态，故修复无效。
2. **`mvn compile` 是绿的（exit 0）**。上述阻断与 4 处 `@RequestMapping` 被吞均为**运行期**问题，
   编译期完全不可见——延续了本仓库"684 例测试全绿却掩盖 P0"的同一方法论缺陷。
3. **前端要的 7 个特效，参考项目 `COM_RAG_System` 一个都没有**，无法照抄，需自研。
   它真正可借鉴的是 4 项：`v-reveal` 滚动入场指令、CSS"地球/网络环"、Hero 3D 视差、bento 栅格。
4. **悬浮球未删干净**：`FloatBall.vue`(109 行) 与 `CustomerServiceBall.vue`(554 行) 仍在仓库，
   全站零引用。是"复活 + 查显示 bug"，不是从零写。
5. **`admin/Dashboard.vue`(1195 行) 是已写好但未接路由的孤儿**；路由实际挂着 155 行的旧 `Main.vue`。
6. **PDFBox 2.0.29 / POI 5.2.5 / easyexcel 已在 pom**，PDF 入库缺的是链路不是依赖。
7. **向量索引已损坏**：`metadata.json` 声明 312 条，`vectors.bin` 仅够 208 条，
   104 篇永久不可召回（`LocalVectorStoreImpl.java:158-164` 只告警不修复）。

## 阶段 1：多 Agent 架构地基

**现状**：1 个 ReAct Agent（6 段 prompt 皮肤）+ 1 条确定性 NL2SQL 管道。
**四件套全缺**：Agent 注册表 / 编排器 / 子 Agent 委派 / Agent 级可观测性。

### 1-1 新增数据表

| 表 | 用途 | 关键列 |
|---|---|---|
| `agent_config` | **Agent 注册表** | `agent_key`(uniq), `name`, `description`, `avatar`, `system_prompt`, `model`, `temperature`, `top_p`, `max_tokens`, `audience`(user/doctor/admin/all), `max_iterations`, `enabled`, `is_default`, `sort_order` |
| `agent_tool_binding` | **per-Agent 工具白名单** | `agent_id`, `tool_name`, `enabled`, `sort_order` |
| `agent_handoff` | **允许的委派关系** | `from_agent_id`, `to_agent_id`, `condition_desc`, `enabled` |
| `agent_run` | **Agent 级可观测性** | `run_id`, `agent_id`, `session_id`, `user_id`, `audience`, `question`, `status`, `iterations`, `prompt_tokens`, `completion_tokens`, `latency_ms`, `error_msg` |
| `agent_run_step` | 运行步骤明细 | `run_id`, `step_index`, `step_type`(llm/tool/handoff), `tool_name`, `args_json`, `result_digest`, `latency_ms` |

种入现有 6 个角色，保证**零回归**（无表/无数据时回退硬编码默认值）。

### 1-2 新增后端组件

| 组件 | 职责 |
|---|---|
| `AgentRegistry` | 从 `agent_config` 加载 Agent 定义（带 TTL 缓存），DB 不可用时回退到原硬编码 6 角色。**替代 `AgentCoordinator.buildDefaultRoles()`** |

| `ToolRegistry` 改造 | 支持按 Agent 白名单过滤 `buildToolsArray()`；保持无绑定时全量（向后兼容） |
| `AgentRunRecorder` | 记录 `agent_run` / `agent_run_step`，提供查询接口 |
| `AgentAdminController` | `/agent/admin/*` CRUD：Agent 增删改查、工具绑定、委派关系、启停、试运行 |

### 1-3 管理端页面

新增「智能体管理」页（管理端菜单），支持：新建/编辑/删除 Agent、绑定工具（多选）、配置委派关系（可视化）、调参、启停、试运行对话。

### 阶段 1 验收标准

1. 管理员在管理端**新建一个 Agent**，刷新后仍在（落库）。
2. 新建的 Agent 在对话中**能被路由命中**（意图/关键词/显式指定）。
3. Agent A **委派给 Agent B** 并把 B 的结果汇总进最终回答（`agent_run_step` 可见 `handoff` 步骤）。
4. 每个 Agent **只能调用被绑定的工具**（未绑定的工具不出现在 function schema 里）。
5. `agent_run` 表能查到每次运行的 token / 耗时 / 迭代数。

## 阶段 2：RAG 知识库与检索增强

### 2-1 新增数据表

| 表 | 用途 | 关键列 |
|---|---|---|
| `kb_data_source` | **数据源注册表**（本地 MySQL / 远端 SQL） | `name`, `jdbc_url`, `username`, `password_enc`, `driver`, `db_type`, `enabled`, `is_default` |
| `knowledge_base` | **多知识库** | `name`, `description`, `kb_type`, `embedding_model`, `chunk_size`, `chunk_overlap`, `data_source_id`, `visibility`(public/role/user), `owner_id`, `doc_count`, `chunk_count`, `status` |
| `kb_document` | 文档 | `kb_id`, `title`, `file_name`, `file_type`, `file_size`, `checksum`, `source_type`(upload/url/news), `status`(parsing/indexed/failed), `chunk_count`, `error_msg` |
| `kb_chunk` | 分块 + 向量 | `doc_id`, `kb_id`, `chunk_index`, `content`, `vector` BLOB(float32 LE), `dim`, `token_count`, `meta_json` |
| `retrieval_log` | **召回评估** | `query`, `kb_ids`, `mode`(hybrid/vector/keyword), `candidate_counts`, `hit_count`, `latency_ms`, `top_k`, `rrf_k`, `hit_chunk_ids`, `gold_chunk_ids`, `recall_at_k`, `precision_at_k`, `mrr`, `rerank_enabled`, `created_at` |

### 2-2 文档解析链路（依赖已在 pom，无需新增）

- `DocumentParser` 接口 + 实现：`PdfDocumentParser`(PDFBox 2.0.29)、`DocxDocumentParser`/`ExcelDocumentParser`(POI 5.2.5 / easyexcel)、`TxtMarkdownParser`、`HtmlDocumentParser`
- `DocumentParserFactory` 按扩展名/MIME 分发
- 上传接口：`POST /kb/{kbId}/documents`（多文件），异步解析 + 状态轮询
- 分块复用 `ChunkUtil`，但**分块参数改为按知识库可配**

### 2-3 向量存储迁移到 MySQL

- 新增 `DbVectorStore implements LocalVectorStore` 接口（保持接口兼容，便于切回文件实现）
- 向量以 `BLOB`（float32 小端）存 `kb_chunk.vector`；检索在应用层按 `kb_id` 过滤后算余弦
- 保留 `LocalVectorStoreImpl` 作为可选后端（配置开关）
- **修复历史损坏**：提供一次 `/kb/reindex` 全量重建，并让 `effectiveCount` 不一致时**自动触发重建**而非仅告警

### 2-4 混合检索优化

现状（`crm/rag/HybridRetriever.java`）：
- 稀疏路 = MySQL `LIKE '%kw%'`（**无全文索引，全表扫**）
- 稠密路 = 向量余弦
- 融合 = 固定 RRF k=60，**无权重、无归一化、无 rerank**
- 缓存 = `size>200` 时整体 `clear()`，**无 TTL、无失效**

改造：
1. **稀疏路**：`news` 与 `kb_chunk` 加 MySQL **中文全文索引（ngram parser）**，用 `MATCH...AGAINST` 打分；保留 LIKE 兜底
2. **稠密路**：改走 `DbVectorStore`，按 `kb_id` 过滤
3. **融合**：支持 RRF（k 可配）/ 加权归一化两种策略，**参数可在管理端配置**
4. **rerank**：新增可开关的轻量 reranker（默认关闭）；实现为**本地交叉特征打分**（词项覆盖 + 位置 + 向量重排），不依赖外部 API
5. **缓存**：改真 LRU + TTL + 写时失效

### 2-5 召回率 / 精确率统计（核心诉求）

- `RetrievalMetricsService`：每次检索落 `retrieval_log`，记录 `recall@k` / `precision@k` / `MRR` / 耗时
- **golden set 落库**：把现有写死的 5 题扩展为可维护的评测集表（含标注相关分块 id）
- 无标注时，用**查询-分块相关性启发式**（关键词覆盖）估算，并在 UI 明确标注为"估算"
- 管理端「RAG 监控」页新增：召回率/精确率趋势、检索耗时 P50/P95、各知识库命中分布、失败查询 TopN

### 2-6 离线可验证的 embedding

- `EmbeddingProvider` 接口 + `OpenAiCompatibleEmbeddingProvider`（现有）+ **`LocalDeterministicEmbeddingProvider`**
  （字符 n-gram 哈希 + TF-IDF 归一化，维度可配，**纯确定性、无网络、可单测**）
- 选择逻辑：配了 `embedding_api_key` 走远程，否则走本地兜底并**在日志与 UI 明确告知**
- 保证：检索算法、融合、rerank、召回指标**全部可离线端到端验证**

## 风险与对策

| 风险 | 对策 |
|---|---|
| 后端启动阻断可能不止 `dataSource` 一处（修完才暴露下一个） | 阶段 0 以"真实启动成功"为唯一验收口径，逐个打通，不做静态推断 |
| 表结构变更影响存量数据 | 所有新表独立，不改既有表；迁移脚本幂等（`IF NOT EXISTS` / `INSERT IGNORE`） |
| 向量迁移到 MySQL 后性能下降 | 按 `kb_id` 分区过滤 + 行数上限；预留 pgvector 迁移接口 |
| 无外部 API key 导致"看起来能跑" | 本地兜底 embedding 确定性可测；UI/日志明确标注当前 provider |
| 前端动效在旧浏览器/暗色模式下出问题 | 全部动效遵守 `prefers-reduced-motion`；暗色回归纳入验收 |
| 改动面大，回归风险 | 每阶段结束跑全量单测 + 真实启动 + 前端构建三件套 |
