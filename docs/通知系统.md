# 通知系统（业务通知 / 用户开关 / 就诊提醒）

> 编写时间：2026-10-10
> 涉及后端：`cn.kmbeast.core.notify.*`、`cn.kmbeast.service.impl.*`、`cn.kmbeast.mapper.*`
> 涉及前端：`views/user/UserSettings.vue`、`views/user/Message.vue`
> 相关文档：`docs/后端开发.md` §3.7、`Data/README.md`（迁移脚本 08）

## 一、这份文档解决什么问题

设置页「通知设置」里有五个开关：系统消息 / 健康提醒 / AI 对话 / 预约提醒 / 商城订单。

**在这之前，这五个开关没有任何后端代码读过，纯装饰** —— 用户把它们全关掉，该来的通知照样来。
各业务模块各自往 `notification` 表里写行，没有任何地方表达过「一条通知该受哪个开关管」。

现在这三个开关（**预约提醒 / 订单通知 / AI 对话通知**）已经是真开关：

- 发送方统一收口到 `UserNotifier`，**发送前先查收件人的偏好**；
- 预约、商城、AI 三条业务线共 **9 个触发点**全部接线；
- 新增「就诊前一天提醒」定时任务（原来完全没有这个功能）；
- 顺带修掉一个真实缺陷：**AI 流式对话里用户中途离开页面，整轮回复会被丢弃且永不入通知**。

两个开关**有意没有接线**（`系统消息` / `健康提醒`），理由见 §八，那是一处产品决策，不该由代码单方面定。

## 二、整体链路

```
  业务动作                     UserNotifier                  NotificationService
┌──────────────┐          ┌────────────────────┐          ┌──────────────────────┐
│ 挂号 / 取消   │          │ ① 查偏好(开关)      │          │ ③ 补 is_read/create_time│
│ 下单 / 支付   │ ───────▶ │   allows()         │ ───────▶ │ ④ insert notification │
│ 发货 / 完成   │  发送     │ ② 组装通知实体      │  落库     │ ⑤ WebSocket 实时推送   │
│ AI 回复完成   │          │   （含去重 sendOnce）│          └──────────────────────┘
│ 定时任务      │          └────────────────────┘
└──────────────┘
       │                          │
       │                          └── source（NotificationSource 枚举）
       │                                决定受哪个开关管 + 落库的 3 个分类字段
       │
       └── 文案统一来自 NotifyTemplates（含跳转链接常量）
```

读的链路：`GET /user/settings` → `UserServiceImpl#buildSettings` → `notification` 五个键；
写的链路：`PUT /user/settings` → `UserServiceImpl#updateUserSettings` → `switch` 到 `user` 表五列；
发送时读的那一份：`UserMapper#getNotifyPreference` → `NotifyPreferenceVO`。

## 三、开关 ↔ 来源 ↔ 落库字段对照表

`NotificationSource`（`cn.kmbeast.pojo.em.NotificationSource`）是这套设计的核心：它把「一条通知从哪来」变成一个枚举，**枚举项与开关一一对应**，发送方就不再需要自己判断。

| 枚举项 | 开关（设置页） | 前端键 | `user` 表列 | `biz_type` | `source` | `message_type` | `notification.type` |
|---|---|---|---|---|---|---|---|
| `APPOINTMENT` | 预约提醒通知 | `appointmentRemind` | `notify_appointment` | `APPOINTMENT` | `SYSTEM` | 5 预约提醒 | 1 预约 |
| `ORDER` | 商城订单通知 | `orderNotify` | `notify_order` | `MALL` | `ORDER` | 6 订单通知 | 3 订单 |
| `AI_CHAT` | AI对话通知 | `aiChatNotify` | `notify_ai_chat` | `AI_CHAT` | `AI助手` | 7 AI对话 | 5 AI对话 |
| `SYSTEM` | 系统消息通知 | `systemNotify` | `notify_system` | `SYSTEM` | `SYSTEM` | 4 系统通知 | 0 公告 |
| `FOLLOWUP` | 健康提醒通知 | `healthRemind` | `notify_health_remind` | `FOLLOWUP` | `SYSTEM` | 3 指标提醒 | 2 随访 |

**`notification.type` 的 5（AI 对话）是本次新增的业务分类**，实体注释已同步补上（原注释只到 4 私信）。
消息中心（`Message.vue`）的 Tab 由 `/message/types` 动态渲染、图标只对 1/2/3 分支判断、其余走 `v-else`，
所以新增分类**前端零改动**；反过来说，**已有分类的数值不允许重排**，否则历史消息会串类。

判定的实现是 `NotificationPreferenceServiceImpl#allows(userId, source)`，三种边界都定过口径：

| 情况 | 结果 | 理由 |
|---|---|---|
| 列值为 NULL | **放行** | 列是 `DEFAULT 1`。反向默认（NULL 当关）会让一次漏跑迁移静默吃掉全站通知，且毫无报错 |
| 用户查不到（已注销/脏数据） | **不投递** | 没有收件人 |
| 查询本身抛异常 | **放行**（记 warn） | 开关读不出来（例如漏跑 08 脚本导致列不存在）不该把下单/挂号一起打挂 |
| `userId`/`source` 为 null | 不投递 | 参数都不全，不可能发对 |

## 四、触发点清单（当前 9 处）

| # | 业务场景 | 代码位置 | 标题 | 幂等 |
|---|---|---|---|---|
| 1 | 挂号成功 | `AppointmentServiceImpl#bookAppointment` | 预约成功 | `send` |
| 2 | 预约被取消（**仅当取消人不是患者本人**） | `AppointmentServiceImpl#cancelAppointment` | 预约已取消 | `send` |
| 3 | 就诊完成（医生端「完成接诊」） | `DoctorWorkServiceImpl#completeAppointment` → `notifyCompleted` | 就诊完成 | `sendOnce` |
| 4 | 就诊完成（医生端「开始接诊」一并置完成） | `PatientDetailServiceImpl#startConsultation` | 就诊完成 | `sendOnce` |
| 5 | 下单成功 | `MallServiceImpl#createOrder` | 订单待付款 | `send` |
| 6 | 支付成功 | `MallServiceImpl#payOrder` | 支付成功 | `send` |
| 7 | 订单状态流转（发货/完成/取消/退款） | `MallServiceImpl#updateOrderStatus` → `notifyOrderStatusChange` | 订单已发货 / 订单已完成 / 订单已取消 / 订单退款中 | `sendOnce` |
| 8 | 就诊前一天提醒（定时任务） | `AppointmentReminderJob#remindFor` | 就诊提醒 | `sendOnce` |
| 9 | AI 回复生成完成（用户已离开页面） | `AiServiceImpl#notifyReplyReady` | AI 回复已生成 | `send` |

几个刻意的口径选择：

- **#2 自己取消自己不发通知**。用户在页面上刚点完「取消预约」，再收到一条「您的预约已取消」是噪音。
  只有**被他人取消**（管理员/医生代操作）才需要提醒，因此代码里先判 `LocalThreadHolder.isSelf(patientId)`。
- **#3 / #4 两条路径都要覆盖**，所以用 `sendOnce`：只要这次预约已经发过「就诊完成」，另一条路径就不再重复。
  只接一条路径是这类改造最常见的漏网之处。
- **#7 用 `sendOnce` 是防管理员双击「发货」**。状态 0（刚下单）与 1（已支付）**不在这里通知** ——
  那是用户自己的动作，已经在 #5 / #6 发过对应文案，再发一遍就是同一件事两条消息。
  这一条由 `NotifyTemplates#orderStatusTitle` 返回 `null` 来表达（null = 该状态不需要通知）。
- **#9 用 `send` 而不是 `sendOnce`**：同一次会话里用户可以多次离开页面、每次生成完成后都该有回告，
  这不算重复。

### 发送失败绝不影响主流程

`UserNotifier#send` 内部吞掉一切 `Exception`、只记 warn 并返回 `false`。
通知是业务的**副作用** —— 一条「预约成功」没发出去，不该让挂号本身失败、更不该让事务回滚把已经占上的号退掉。

补充一个实现细节（回答「吞掉异常会不会把事务搞坏」）：`NotificationServiceImpl#save` **本身没有 `@Transactional`**，
所以它不构成新的事务边界，异常也就不会被 Spring 标记成 rollback-only。通知行与业务改动在**同一个事务**里提交：

- 业务回滚 → 通知一起回滚，不会有「预约成功了但其实失败了」的孤儿通知；
- 通知插入失败（例如表不存在）→ InnoDB 只回滚该语句，业务事务照常提交，主流程不受影响。

## 五、幂等（去重）设计

### 去重键是五元组，而且**必须包含 title**

`UserNotifier#sendOnce` 先去查：
`NotificationMapper#countBizNotification(userId, bizType, bizId, messageType, title)`。

**为什么不能只用 `(user_id, biz_type, biz_id, message_type)`**：

- 一笔订单天然要发四条（创建/支付/发货/完成），`biz_type` 与 `message_type` 全都相同，只靠它会去重成一条；
- 一次预约天然要发两条（挂号成功 + 前一天提醒），同理；
- `biz_id` 在表里是 `bigint unsigned`，因此也**没法**把 `messageType` 拼进 `biz_id` 造一个组合键。

因此把 title 纳入键。为了让「同一件事」在代码里只有一个写法，**所有标题集中在 `NotifyTemplates`** ——
文案散落各处时，同一件事在两处写了两遍标题，去重会**静默失效**。

### 刻意不做时间窗

查询里没有 `create_time` 范围条件，即「这条通知一旦发过就永远不再发」。
对当前这三个使用场景（就诊提醒 / 就诊完成 / 发货）而言这正是想要的语义；
如果将来出现「每周一提醒」这类周期性通知，必须给去重键加时间维度，不要直接复用 `sendOnce`。

### 去重查询失败时**照发**

宁可偶发重复，也不要因为一次查询报错让用户的就诊提醒永远发不出去。

## 六、就诊前一天提醒（定时任务）

`AppointmentReminderJob`，默认**每天 19:00** 扫「明天」的预约并发提醒。

```yaml
notify:
  appointment-reminder:
    cron: "0 0 19 * * ?"   # 默认值；置为 "-" 可关闭本任务
```

不配置该项时用默认值（`@Scheduled(cron = "${notify.appointment-reminder.cron:0 0 19 * * ?}")`）；
配置成 `-`（或 `-` 以外的非法值会启动报错，故用 `-`）即可关掉。

### 为什么只能做「前一天」提醒

`appointment` 表只有 `appointment_date`（**日期粒度**），排班的 `time_slot` 只有
`morning` / `afternoon` / `evening` 三个字符串，**没有具体钟点**。
所以「提前 1 小时提醒」在现有数据模型上**根本做不到** —— 这不是偷懒，是数据不允许。
要做精细提醒，得先给排班加钟点字段 —— 那是一次数据结构变更，不在本次范围。

### 目标筛选在 SQL 里做

`AppointmentMapper#queryReminderTargets`：

```sql
WHERE a.appointment_date = #{appointmentDate}
  AND a.status IN (0, 1)                                  -- 待接诊 / 已预约
  AND (u.notify_appointment = 1 OR u.notify_appointment IS NULL)
ORDER BY a.time_slot ASC, a.serial_number ASC
```

- **开关过滤放在 SQL**：关掉开关的用户在数据库层就被滤掉，批量路径不做 N 次偏好查询；
- `IS NULL` 也要算进来，与 §三 的「NULL 视为开启」同一口径；
- `status IN (0,1)`：已完成(2)与已取消(3)不该再提醒。

### 幂等与容错

定时任务没有天然的一次性保证（服务重启、多实例部署、手动触发都会重跑），因此逐条走 `sendOnce`。
整个方法体包在 `try/catch` 里：定时线程抛出的异常不会让进程退出，但会丢掉本轮剩余处理并留下裸堆栈，
这里兜住并记明「跑失败了」，下一次调度照常。无目标时不打 info 日志，避免没有预约的夜里天天刷屏。

> 多实例部署提示：`sendOnce` 是「先查后插」，两个实例同时进入同一毫秒仍可能各插一条。
> 单实例部署没有这个问题。要严格唯一，需要给 `notification` 加业务唯一键
> （当前 `biz_id` 是 `bigint unsigned`，做不到把 messageType 拼进去，所以这条路暂时不通）。

## 七、AI 对话通知（顺带修掉的一个真实缺陷）

`AiServiceImpl#chatStream` 把回复通过 SSE 推给前端。**客户端中途断开**（切标签页、关页面、刷新）时，
`AiController` 的 SSE 回调会抛 `RuntimeException("SSE client disconnected")`。

**原实现**：这个异常一路冒到 `chatStream` 的 `catch (Exception)` → 直接 `return`。
后果不只是「没推送」—— **整轮 AI 回复既不推送也不入库**，用户切个标签页就永久丢掉一条
（可能是深度思考跑了几十秒才生成的）回答，数据库里没有任何痕迹。

**现在的处理**：新增 `StreamSink` 把「客户端断开」与「真的出错了」区分开：

| 异常 | 处理 | 理由 |
|---|---|---|
| 消息含 `SSE client disconnected` | 记 `clientGone` 标记，**不抛**，停止继续推送 | 生成继续跑完 → 回复照常入库 → 事后回告 |
| 其它 `RuntimeException` | **照旧向上抛** | 真故障不许被伪装成「用户离开了」 |
| `message == null` | 向上抛 | 同上 |

生成循环里加了上限：客户端已断开且回复长度达到 `ABANDONED_REPLY_MAX_CHARS = 4000` 时提前结束，
避免「没人收还硬写几万字」把线程占用拖长（这是原设计在意的问题）。
生成结束后若 `clientGone && 回复非空`，调 `notifyReplyReady` 发「AI 回复已生成」通知，
正文里带上用户提问的前 40 字（`NotifyTemplates#aiChatDone` 会截断并加省略号）。

> 关联：`docs/智能体架构.md`。这个修复同时让 `docs/缺陷与改进路线图.md` §2.3 E1
> 里「AI 关键链路无冒烟测试」多了一层单测保护（`AiStreamSinkTest`）。

## 八、有意**没有**接线的两个开关

这两个开关在设置页是有的、值也照样存库，但**没有任何发送方被它们拦住**。这是明确决定，不是遗漏：

| 开关 | 为什么先不接 |
|---|---|
| **健康提醒通知**（`notify_health_remind`） | 现在唯一的发送方是「健康指标超标告警」（`UserHealthServiceImpl#dealMessage`）。那属于**安全类提醒** —— 做成用户能一键关掉，等于让人关掉自己的异常指标告警。接线前需要先确认产品口径 |
| **系统消息通知**（`notify_system`） | 发送入口是 `MessageService#systemInfoUsersSave`（管理员群发广播），那条链路是「一次写给一批人」，与 `UserNotifier` 的「单收件人 + 偏好判定」形状不同，需要单独改造批量路径 |

两个枚举项（`SYSTEM` / `FOLLOWUP`）已经建好、字段与判定的 `switch` 分支也都在，
**将来接线只需在发送处改一行**，不用再动枚举。

### 另一个已知边界

`NotificationMapper#batchSave`（管理员群发走的那条）**只写 9 列**，没有 `title` / `biz_type` / `biz_id` / `link_url`；
`MessageServiceImpl#toNotification` 也没给这几个字段赋值。所以群发通知在消息中心是**没有标题、点不动**的，
与 §九 的「业务通知带标题 + 可点击」不一致。本次未改动它（属于系统公告链路，不在本次范围），
列在这里以免被误认为已支持。

## 九、消息中心前端的改动（本次顺带修）

`notification` 表有 `title` 与 `link_url`，但 `MessageServiceImpl#toMessageVOs` 一直**只搬运 content**，
于是「预约成功 / 订单已发货」这类通知在消息中心只剩一句正文，看不出发生了什么；
正文里那句「点击前往查看」也点不动。修补：

| 文件 | 改动 |
|---|---|
| `pojo/vo/MessageVO.java` | 新增 `title`、`linkUrl` 两个出参字段 |
| `service/impl/MessageServiceImpl.java` | `toMessageVOs` 搬运 `title` / `linkUrl` |
| `views/user/Message.vue` | 有 title 时加粗显示标题；有 linkUrl 时显示「查看详情 >」，点击**先标已读再跳转** |

跳转路径常量与前端路由一致（`NotifyTemplates`）：`/user/appointment`、`/user/mall`、`/user/ai-analysis`。
标已读失败（例如被并发删掉）**不拦着跳转** —— 用户点「查看详情」的意图是去看那条预约/订单。

> 已知边界：WebSocket 实时推送的消息体（`NotificationServiceImpl#save` 里的 `data`）不含 `linkUrl`，
> 所以**顶部铃铛的实时弹窗点不跳转**，需要回到消息中心才能点。属于前端铃铛的后续增强项。

## 十一、以后新增一种业务通知怎么做

1. 在 `NotificationSource` 加一个枚举项，绑定 `(bizType, source, messageType, type, 开关名, 偏好列)`；
   **必须能对应到恰好一个用户开关** —— 没有对应开关的，先想清楚归谁管再加；
2. 在 `NotifyTemplates` 加标题常量与正文构造函数（复用 `nz` / `truncate` / `fmt` 兜底，别让正文出现 `null`）；
3. 发送处注入 `UserNotifier`，写一行 `send(...)` 或 `sendOnce(...)`：
   - 属于「天然一次性」的业务动作（下单、支付、挂号）→ `send`；
   - 可能被重复触发（双击、多入口、定时任务）→ `sendOnce`；
4. 控制器的 `@Protector` / 越权判断沿用既有写法（通知自身不需要新增权限）；
5. 补单测：至少覆盖「开关关掉时不落库」与「落库字段正确」两条。
