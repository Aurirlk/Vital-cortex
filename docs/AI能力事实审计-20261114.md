## 1. 防幻觉：逐段解剖真实管线

### 1.1 用户端唯一主链路

前端反查结果（`Assistant.vue:306`、`AiAnalysis.vue:1190`、`NavAssistant.vue:272/305/347`）：

```
用户输入
  ↓  POST /ai/chat 或 /ai/chat/stream
AiServiceImpl.chat() / chatStream()
  ├─ buildHealthContext(userId)      读 user_health（真实 MySQL）
  ├─ buildArticleRagContext()        HybridRetriever：向量×LIKE → RRF(top6)
  ├─ knowledgeGraphService.getRelatedContext()   GraphRAG（Neo4j→本地三元组→词表）
  ├─ buildDrugContext()              读 ai_data/drugs.json（最多 30 条）
  ├─ buildMessagesArray()            system prompt + 历史（ContextCompressor 压缩）
  ├─ ChatToolLoop.run()              ≤3 轮工具（身份只认 LocalThreadHolder）
  ├─ LLM 调用（DeepSeek / 本地 vLLM）
  └─ 三个 guard → 追加文本 → 落库
```

**关键事实**：`/user/chat`（8 工具 ReAct、`SeaChatWorkflow`、5 轮自主决策）**前端零调用**——
全仓只有一条注释提到它。用户侧实际走的是 `AiServiceImpl` 自带的 `ChatToolLoop`（3 轮）。
所谓「ReAct Agent 工具增强推理」在用户端是**死链路**，只有医生端 `/doctor/chat/stream` 在用（`DoctorChat.vue:315`）。

### 1.2 「三层门」逐行判定

| 类 | 行数 | 实际逻辑 | 命中后的行为 | 能否阻止错误答案 |
|---|---|---|---|---|
| `SynthesisGuard` | 51 | 6 个填充词（嗯嗯/哈哈…）+ 句子两两相等 | `log.warn`（`AiServiceImpl:295/595`） | ❌ 只写日志 |
| `OutputValidator` | 81 | 2 条剂量正则 + 5 个医疗词 | 在回答**尾部追加**两句提示（`:301-306`） | ❌ 正文一字不改 |
| `SignalDetector` | 35 | 6 个词：急救/120/紧急/危重/昏迷/大出血，匹配**用户输入** | 追加「请拨 120」 | ❌ 且词表非临床 |

`SignalDetector` 的致命点：**「胸口压得慌、出冷汗、左臂发麻」不命中任何关键词**。
这不是「红旗症状规则」，是 6 个口语词。而 `OutputValidator` 的 5 个词是
`诊断/处方/用药/治疗方案/手术`——命中只会挂一句免责声明，与答案对错无关。

**所以：系统对「把心梗说成胃食管反流」这种最危险的错误，既不会发现、也不会拦截、也不会降级。**
README 已经承认这一点；`技术问答.md:164-168` 却仍把它列为「五层护栏（GraphRAG 约束 / 防端水 /
输出验证器 / 提示词约束 / 知识库 RAG）」并标注作用层级——这份文档需要改。

### 1.3 检索层的四个硬伤

1. **证据量极小**：`RAG_ARTICLE_LIMIT=6`、`RAG_CONTENT_MAX_LENGTH=300`（`AiServiceImpl:135-136`）
   → 送进模型的证据上限 **1800 字**，而单篇 `news.content` 通常 1000 字以上，
   实际只截取「关键词命中片段」。医学问题靠 1800 字片段支撑，本质是装饰。
2. **没有 rerank**：`RAG子系统.md:136` 自己承认「❌ 无 cross-encoder」，RRF 分数直接排序。
3. **向量路随时整条失效**：`HybridRetriever:112` catch 住异常后 `log.warn` 继续，退化为纯 LIKE。
   而当前磁盘状态仍是 208/312 错位——**下标 208~311 的 104 篇永久不可召回**。
4. **关键词兜底很粗暴**：Dify 提取失败 → 取用户原文前 10 个字当关键词（`AiServiceImpl:877-879`）。
   「我最近总是头晕乏力想吐怎么办」→ 关键词「我最近总是头晕乏力想」，LIKE 命中率接近随机。

### 1.4 引用链路的真相

`AiServiceImpl:914` 拼 `[ID:123]`，`:928` 写「必须基于以上文章内容回答，引用时标注 [ID:x]」。
**全仓 grep `\[ID` 只有这两处**：一处是往上下文里塞 ID，一处是给模型的文字要求。
没有任何代码：

- 解析模型输出里的 `[ID:x]`
- 校验 x 是否在本次召回集合里
- 校验被引段落是否真的支持该结论
- 引用缺失/伪造时降级或拒答

结论：**「引用溯源」= 一句 prompt。模型写 `[ID:999]` 或干脆不写，系统完全无感。**

### 1.5 「RAGAS」是什么

`RAGEvaluationServiceImpl:236-256`：

```java
private double coverage(String retrieved, String goldAnswer) {
    for (int i = 0; i + 4 <= g.length(); i++) {
        String seg = g.substring(i, i + 4);
        if (r.contains(seg)) hit++;
    }
    return (double) hit / total;
}
```

即：**把标准答案切成 4 字滑窗，数有多少片出现在检索文本里**。
它衡量的是「检索到的文本是否包含标准答案的字面」，既不涉及 LLM 判定，
也不涉及**模型实际生成的答案**。把它叫 `faithfulness（忠实度）` 是术语误用——
RAGAS 的 faithfulness 衡量「答案的每个论断能否由 context 推出」。
更关键：`rag_eval_case` / `rag_eval_run` 都是 **0 行**，这个看板从来没跑出过数据。

### 1.6 真正做硬的地方（不是防幻觉）

这个项目里确实有几处防线是**代码级、fail-closed、有反向测试**的，但方向都不是「防医学错误」：

| 机制 | 防的是什么 | 证据 |
|---|---|---|
| `ToolContext` / `LocalThreadHolder` 单一身份入口 | 越权读他人数据 | `ChatToolLoop` 类注释「绝不信任 LLM 回传的 userId」 |
| `DataAgentPipeline.safeRewrite()` | SQL 逃逸/跨租户 | 子查询、CTE、隐式逗号连接、白名单外表四类拦截 |
| `MemoryPoisoningValidator` | **提示词注入 / 记忆投毒** | 整批 fail-closed，命中「忽略之前」等即拒写 |
| `AuthSessionManager` refresh 轮换 | Token 重放 | Redis `getAndDelete` 原子一次性 |
| `ContextCompressor` + `TokenBudgetManager` | 上下文爆炸 | 预算 ≤ 模型窗口 50%，超限抛错而非静默截断 |

**这是这个项目真正的技术资产：一套相当认真的「LLM 应用安全工程」。**
但它保护的是「数据不被越权访问、提示词不被污染」，不是「医学结论正确」。
两者常被混为一谈，也是所有虚标的心理来源。

### 1.7 一句话总结第 1 问

> 当前系统的「防幻觉」= ①prompt 里写「严禁编造医学事实」②检索 1800 字证据
> ③回答完追加一句免责声明。**没有任何一条能在答案生成后判断它对不对，也没有任何一条能在
> 低置信时拒绝回答。** 这不是「防线薄弱」，是「防线只存在于文案里」。

### 2.4 最危险的定位问题不是商业，是合规

系统对外呈现的是「全科医生 Agent → 症状分析 + **分诊建议**」（README:276、功能文档:114、技术问答:50），
同时 prompt 里写「三甲医院资深全科医生」「初步分析与可能性预测」。
在中国监管语境下，「分诊建议」+「症状分析 + 可能性预测」已经踩到**互联网诊疗/医疗器械软件**的边界：

- 若定位 C 端健康科普 → 必须明确「不涉及诊疗」，现在的角色命名与话术相反；
- 若定位医院内部辅助 → 需要二类器械注册、等保三级、临床验证、医生复核留痕，**四样都没有**。

`README:22` 的免责段是对的，但它和产品页的「全科医生」「分诊建议」是**互相抵消**的两套话术。
对外材料只要同时出现这两句，就是自证其罪。

### 2.5 该选哪条路（我的判断）

二选一，不要第三条：

- **A. 慢病自我管理工具**（推荐）：只服务「有明确指标、需长期跟踪」的人（高血压/糖尿病/血脂异常）。
  AI 的职责收窄为三件可验证的事：读你的指标 → 解释趋势 → 提醒复查。**明确不做症状诊断**，
  角色名从「全科医生」改为「指标解读助手」。这条路的护城河是**数据连续性**，不是模型。
- **B. 医生端数据助手**：只做 `/doctor/chat` + `DataAgentPipeline`，卖给体检中心/诊所。
  这条路要求把「患者数据授权 + 审计留痕 + 结论可回溯」做到满分——项目在审计和隔离上已有底子，
  是唯一「现有代码能直接支撑」的方向。
- ❌ **不要**继续做「个人健康超级 App + 医院级平台」：39 篇内容 + 98 条对话 +
  0 份知识库文档，任何一条路都还没走通，同时走三条必然全废。

### 3.3 诚实的距离表述

不要在「几年」这个尺度上回答，因为两者不在同一品类：

- WiseDiag 是**医学基础模型 + 临床交付体系**（模型 → 评测 → 医院准入 → 专家分身 → 商业闭环）；
- 本项目是**LLM 应用集成层**（Spring Boot 业务系统 + 外部模型 API + 一层很薄的 RAG）。

这个距离不是「差 3 年」，而是「**差一个物种**」。
任何工程优化（换 pgvector、加 rerank、接 LangGraph）都不会缩小这个距离，
因为距离的分子在**数据资产与临床验证**，而这两样需要的是医学团队和医院关系，不是代码。

**唯一有意义、且能在当前架构内做到的追赶方式**：放弃通用医学能力，改比「单场景闭环」。

举一个可验证的例子——只做高血压管理：

1. 用真实 `user_health` 指标（现在有数据模型但用户量≈0）建立 90 天血压趋势；
2. 把《中国高血压防治指南》的**可执行规则**写成硬编码判定（≥140/90 连续 3 次 → 提示复诊；
   ≥180/110 → 立即就医），这是**代码级**的，不依赖模型；
3. AI 只做「解释这条规则为什么触发 + 生成复诊摘要」，不产生任何新医学结论；
4. 用「假阴性评测集」验证：构造 200 条含危险信号的真实描述，统计规则漏检率 → 这个数字可以对外说。

这条路的可行性远高于「做医学大模型」，而且能把现有资产（指标模型、审计、隔离、数据智能体）
全部用上。但它要求先承认：**通用问诊这条路，以当前资源配置走不通。**

### 3.4 一个必须说清的成本事实

WiseDiag 的护城河里，最硬的一条不是模型参数，而是**36 万条问答对 + 50 位专家监督微调 + 300 家医院的复核数据**。
这些是「有执照的人花时间产出的数据」，不是爬来的。本项目若要在这条线上有任何可信度，
第一步不是改代码，而是找一位愿意签字的临床医生，把「哪些话绝对不能说」写成规则表。
在没有这一步之前，所有「医疗 AI」的宣称都无法落地。

## 5. 若要真正做「防幻觉」，最小可信集（5 件事，都有验收口径）

1. **引用强校验**（1 天）：正则抽 `[ID:x]` → 校验 x ∈ 本次召回 ID 集合；
   不合法则剥离该标注并在前端提示「本条引文未通过校验」。验收：伪造 `[ID:999]` 的答案必须被剥离。
2. **红旗症状硬规则**（2 天）：≥30 条规则（胸痛+冷汗、单侧无力+言语不清、呕血、意识改变…），
   命中即**在生成前**插入强制就医段，不依赖模型。验收：构造 50 条危险描述，漏检率必须为 0。
3. **低置信拒答**（2 天）：检索最高分低于阈值 或 召回为空 → 直接回「本站没有足够资料，建议线下就医」，
   不调用模型。验收：无检索命中时，模型调用次数必须为 0（日志计数）。
4. **假阴性评测集**（3 天）：200 条「有病但描述模糊」的样本 + 200 条正常样本，
   人工标注「是否应提示就医」，每次改动跑一遍，记录漏检率/误报率。
   这是**唯一能对外说数字**的东西，比 RAGAS 有意义得多。
5. **医生复核留痕**（3 天）：高危回答进入 `audit_log` 待复核队列，医生端有「确认/驳回」，
   驳回原因回写。验收：`audit_log` 中高危条目必须有复核人字段。

这五件事做完，「不能保证不漏诊」才能变成「已知漏检率 X%」——这是一个可辩护的工程状态。
