## 0. 名词澄清：项目里有几个「智能体」？（2026-10-07 代码级清点）

日常沟通里「AI 助手 / AI 医生 / AI 医生助手 / 数据智能体」经常混用，容易误以为是四套系统。
按代码实测，**它们对应的是「两套独立实现 + 一组角色配置」**：

| 名词 | 真实身份 | 是不是独立实现 | 代码位置 |
|------|---------|--------------|---------|
| **数据智能体** | 受控 NL2SQL 十步流水线 | ✅ **唯一真正独立的 Agent** | `core/nl2sql/`（24 个类）+ 3 个控制器 |
| **AI 助手** | 一个**页面名**（"健康助手"）+ 一个**角色值**（`consultant`） | ❌ 不是独立实现 | `views/user/Assistant.vue` → `/ai/chat` |
| **AI 医生** | **6 个角色 persona 的集合**（纯提示词配置） | ❌ 不是独立实现 | `config/AiPromptConfig.java:63-95` |
| **AI 医生助手** | ⚠️ **全仓 0 命中，不存在** | ❌ 虚构名词 | — |

### 0.2 「AI 医生」到底是什么

它是 **6 个角色 key 的集合**，不是有工具、有记忆、能编排流程的独立 Agent：

| 角色 key | 中文名 | 关键词表 |
|---------|--------|---------|
| `doctor` | 全科医生 | 症状 / 疾病 / 疼痛 / 发烧… |
| `nutritionist` | 营养师 | 饮食 / 营养 / 减肥 / 卡路里… |
| `psychologist` | 心理咨询师 | 心理 / 情绪 / 焦虑 / 抑郁… |
| `analyst` | 报告分析师 | 报告 / 体检 / 指标 / 化验… |
| `consultant` | 健康助手 | 健康 / 养生 / 运动 / 锻炼… |
| `general_assistant` | 全能助手 | 空表（默认兜底） |

每个角色**只有一段 systemPrompt 文本 + temperature/topP**，没有任何工具、记忆或流程编排。
存储介质是 `./config/prompts.json` + 静态 Map，**完全不落库**（`ai_config` 表只有 provider/api_key/model 等连接参数）。

⚠️ **这 6 个 key 被重复定义在三处**，且已出现口径漂移：
- `AiPromptConfig.java:63-69`（管提示词）
- `AgentCoordinator.java:35-68`（管路由）
- `AiServiceImpl.java:578-579`（统计接口硬编码，**只有 5 个，漏了 `consultant`**）

**配置界面**在 `views/admin/SystemConfigManage.vue`（「系统配置」菜单内），不是 `AiDoctorManage.vue`
——后者 650 行完整实现但**零路由引用，是死代码**。

### 0.3 「AI 医生助手」从何而来

全仓（含 `.md`、`.sql`、`.vue`）grep **零命中**。它最可能是把下面两处文案误读成了产品名：

- `BaseReActAgent.java:75-77` 的 prompt 文案「推荐 AI 医生……我们有以下 AI 医生角色」——描述的是"选角色"这个动作
- `NavAssistant.vue:24-27` 的 UI 按钮 `<strong>AI 医生</strong>`（该组件本身也是死代码）

## 2. Multi-Agent 协调器（AgentCoordinator）

`AgentCoordinator` 维护一个有序角色表 `AGENT_ROLES`（`LinkedHashMap`），默认 6 个角色：

| 角色 key | 展示名 | 定位 |
|----------|--------|------|
| `doctor` | 全科医生 | 症状 / 疾病 / 用药 |
| `nutritionist` | 营养师 | 膳食 / 营养 |
| `psychologist` | 心理咨询师 | 情绪 / 睡眠 / 压力 |
| `analyst` | 报告分析师 | 体检报告 / 指标解读 |
| `consultant` | 健康顾问 | 通用健康咨询 |
| `general_assistant` | 全能助手 | 兜底（默认回落） |

**路由算法**（`selectAgent`）：
1. 遍历每个角色的**外部化关键词表**，对用户问题做子串匹配，命中累加得分；
2. 取最高分角色；并列或零命中时回落 `general_assistant`。

**AG-11 整改（关键词外部化）**：关键词表不再硬编码，改为可在 `crm.intent.keywords` 配置中覆盖（`@PostConstruct` 时合并），无需改代码即可调整意图识别策略。

## 3. ReAct Agent（推理层）

实现方式：**基于 OpenAI function calling**（非正则解析），由 LLM 自主决定调用哪些工具。核心类：

| 类 | 职责 |
|----|------|
| `BaseReActAgent` | 通用骨架：有界线程池 + 调用超时、工具并行调用、LLM 失败重试、工具轨迹（`ToolResult`）记录 |
| `ReActAgent` | 末轮总结（基于工具结果生成自然语言回答）、去重、循环检测（防无限工具调用） |
| `StreamingReActAgent` | SSE 流式输出版本（资源随连接释放） |

**工具集**（`crm/agent/tool/`）：

| 工具类 | 名称 | 功能 |
|--------|------|------|
| `SearchDrugTool` | `search_drug` | 药品检索（drugs.json） |
| `GetHealthDataTool` | `get_health_data` | 用户健康指标 |
| `SearchKnowledgeTool` | `search_knowledge` | 知识库语义检索（RAG） |
| `WebSearchTool` | `web_search` | 联网搜索 |
| `GetChatHistoryTool` | `get_chat_history` | 会话历史 |
| `ExecuteSqlTool` | `execute_sql` | 只读 SQL（经 `SqlGuard` 守卫 + 租户隔离） |

支撑类：`ToolArgsValidator`（参数校验，含 4 个单测）、`ToolRegistry`、`Tool`/`ToolContext`、`AiSessionContext`。

**检查点 / 审计**：工具调用轨迹（参数、结果、状态）随会话落库，可回放某次对话调用了哪些工具、参数与结果。

## 4. Provider 抽象层（core/provider）

接口 `LLMProvider`：`chat`、`stream`、`getId`、`getCircuitBreaker`。

| 实现 | ID | 说明 |
|------|----|------|
| `DeepSeekProvider` | `deepseek` | 默认厂商 |
| `LocalVllmProvider` | `zhikangyun-local` | 本地微调模型，默认基址 `http://localhost:8000/v1`（OpenAI 兼容） |

**工厂 `LLMProviderFactory`**：
- `init()` 从 `AiConfig.getProvider()` 读取激活厂商；
- `normalize()` 归一化：`local / vllm / zhikangyun-local / zhikangyunlocal` → `zhikangyun-local`；其余回落 `deepseek`；
- 构建共享 `OkHttpClient`（连接/读超时来自配置，连接池 10 × 5min）。

**熔断器 `CircuitBreaker`**：三态 `CLOSED / OPEN / HALF_OPEN`。`defaultFor()` 默认阈值：错误率 50%、统计窗口 60s、OPEN 维持 30s、最小触发调用数 5。`beforeCall / onSuccess / onFailure` 驱动状态流转，每个 Provider 内置独立熔断器；OPEN 时抛 `CircuitBreakerOpenException` 快速失败。

> 遗留：`LLMFactory`（旧注册式工厂）仍在，新代码统一走 `LLMProviderFactory`。

## 6. 数据流

```
用户问题
  → AgentCoordinator.selectAgent()        → 选定角色（含 system prompt）
  → ReActAgent.run() 循环（≤5 轮）:
        LLM(function calling) → 解析 tool_calls
        → ToolRegistry 执行工具（含 ToolArgsValidator 校验 / SqlGuard 守卫）
        → 工具轨迹落库
        → 观察结果回填 prompt
  → 末轮总结 → 返回 / 流式推送（SSE）
        所有 LLM 调用 → LLMProviderFactory → Provider(+熔断器) → 上游厂商
```

## 10. 管理员的三项管理能力（2026-10-07 新增）

都落在 `system_config` 表的 `data_agent` 分组（**复用既有表，未建新表**），
种子脚本 `Data/03_数据脚本/seed_agent_config.sql`，共 21 个键，改完 **10 秒内生效**（`DataAgentConfigHolder` 的 TTL）。

### 10.1 按使用者分层管理

**问题**：此前 4 个开关（`enabled` / `report-enabled` / `max-rows` / `query-timeout`）是**全局共享**的 ——
医生端和用户端只能同一套限流。但两端的实际诉求不同（医生端查患者数据、多表 JOIN 更多，需要更宽的行数）。

**方案**：复用项目内已有的 `preset-questions-user` / `preset-questions-doctor` **key 后缀范式**，
每个键有「无后缀全局值」与「带端后缀覆盖值」两档：

```
max-rows          = 200   ← 全局（保持向后兼容）
max-rows-user     = 200   ← 用户端覆盖
max-rows-doctor   = 500   ← 医生端覆盖
```

读取规则（`DataAgentConfigHolder.rawForAudience`）：
1. 有端后缀且**非空** → 用端侧值
2. 否则用全局值
3. 否则用代码默认值

⇒ **不配置端侧值时行为与改造前完全一致**，零回归风险。管理端用「输入框留空 = 跟随全局」表达。

**链路**：`DataAgentQaService.query()` 按 `roleId == 3` 判定 audience
→ `DataAgentPipeline.run(req, ownerId, sink, audience)`（`audience` 是普通字段 + finally 清空，因为流水线单线程串行）
→ `execute()` 用 `getMaxRowsFor(audience)` / `getQueryTimeoutFor(audience)`。

### 10.2 上下文压缩（真正接线）

**改前**：`AiServiceImpl.buildMessagesArray()` 是 `for (i < history.size())` **全量历史进 prompt**，
超预算时 `TokenBudgetManager` 直接**抛异常**让用户重开会话。
管理员在「智能体管理」里能配的「上下文轮数」此前**零业务读取**（装饰性配置项）。

**改后**（`AiServiceImpl.appendCompressedHistory()`）三层压缩：

| 层 | 键 | 默认 | 做法 |
|---|---|---|---|
| 条数截断 | `context-rounds` | 10 轮 | 只保留最近 N×2 条 |
| 字符预算 | `context-max-chars` | 4000 | 超出时从**最旧**整条丢弃（不做中间截断，避免破坏"最近若干轮"的语义连续性） |
| 滚动摘要 | `context-summary-threshold` | 12 | 被丢弃条数 ≥ 阈值时，用**关键词频次提取**生成一条 system 摘要 |

⚠️ 摘要**刻意不调 LLM** —— 那会让每次请求多一次模型调用（成本 + 延迟 + 失败风险）。

### 10.3 长短期记忆（接线 + 声明更正）

**改前**：`AgentMemoryService` 治理质量上乘（1000 用户 LRU + 30 分钟定时清理 + 不可变副本），
但**全仓只有 3 个 REST 端点调用它** —— 偏好可通过 API 读写，却**永远不进入 prompt，对用户不可见**。

**改后**：
- `BaseReActAgent.buildMemorySection()` → ReAct 链路的 system prompt（上限 800 字符）
- `DataAgentPipeline.safeMemory()` → NL2SQL 的 `{evidence}` 段（上限 400 字符）

两条链路都遵守：**取不到登录身份就不注入**（绝不跨用户读偏好）、超限保留最新、异常降级为不注入。
注入段带一句「与用户当次明确要求冲突时以当次要求为准」，避免陈旧记忆压过当次指令。

> **为什么 NL2SQL 拼进 `{evidence}` 而不是新开占位符**：`evidence` 语义是"补充模型不知道的业务语义"
> （术语字典 + 口语别名→列名），用户偏好同属此类；而 `previous_step_results` 语义是"前序步骤的真实数据"，
> 塞进去会让模型误以为那是查询结果。**不动 prompt 模板，零模板兼容风险。**

**声明更正**：`AgentMemoryService` 类注释曾声称提供「长期记忆、语义记忆、用户偏好记忆」三种，
但 `loadFromDisk` 只读 `preferences` 一个分区 —— **另两种不存在实现**，属注释虚标，已更正并被单测锁住。

### 10.4 沙箱管理（新增字节维度）

「沙箱」在本项目的实际含义是**三层防护**：

| 层 | 机制 | 是否可配置 |
|---|------|-----------|
| ① 词法守卫 | `MySqlAiSqlGuard`：禁 DML/DDL、禁黑名单表、禁子查询/CTE、禁隐式逗号连接 | `sandbox-guard-enabled`（**生产不建议关**） |
| ② 租户隔离 | `TenantSqlRewriter.rewriteAll()` 逐表覆盖租户列 | 始终开启（代码内强制） |
| ③ 账号级只读 | `ai_ro` 账号只有 SELECT | `sandbox-readonly`（**只读标记**，由程序回写） |

**新增维度**：`sandbox-max-bytes`（默认 512 KB）。
此前只有 `max-rows`（行数）——一个 50 列的宽表 200 行轻松就是几 MB JSON，
全部塞进 prompt 会挤爆预算，而 `TokenBudgetManager` 只在**请求前**校验历史，不校验 LLM 返回结果。
超预算时截断并在末尾追加提示行，**不抛异常**（数据智能体应"尽力返回部分结果"而非整体失败）。

管理端「沙箱管理」Tab 用**红/绿告警**明确展示三层防护现状 —— 只读源未配置时直接告诉管理员去执行哪个脚本，
避免"以为已隔离、实际还在用主账号"。
