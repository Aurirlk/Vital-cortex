## 一、冗余全清单（已逐项验证）

### 🔴 缺陷 1：标签表双轨（`tags` + `post_tag`）

**证据**：`post_tag` 表**没有任何字段引用它**（`information_schema` 全库扫描 `post_tag*` 零命中）——它是彻底的孤儿表。

| tags (5行) | post_tag (6行) |
|---|---|
| 饮食健康 | 健康生活 |
| 运动健身 | 疾病求助 |
| 心理健康 | 用药经验 |
| 疾病预防 | 心理交流 |
| **养生保健** | 运动分享 |
| | **养生保健** ← 重复 |

`news.tag_id` 和 `post.tag_id` **都指向 `tags`**，`post_tag` 完全没被用上。

**处置**：合并为 `tags`，加 `sort_order`；数据并集去重；删除 `post_tag`。

---

### 🔴 缺陷 2：内容表双轨（`news` + `post`）

**证据**：两表结构高度同质，实际内容也同质——都是健康科普文章。

| news (9字段) | post (16字段) |
|---|---|
| `name`(标题) | `title` |
| `content` | `content` |
| `cover` | `cover` |
| `tag_id` | `tag_id` |
| `is_top` | `is_top` |
| `reader_ids`(已读人) | `view_count`/`like_count`/`comment_count` |
| `is_banner`(轮播) | `status`(草稿/发布) |
| — | `user_id`(作者) |

实际数据：
```
news#1  春季养生指南：中医教你调理肝气
news#4  体检报告里的血脂指标怎么看
post#2003 春季养生：如何预防感冒
post#2005 颈椎病的预防和保健
```
**同一类内容，两套表，两个前台列表。**

**处置**：合并为 `content` 统一内容表，用 `content_type` 区分「资讯 / 帖子 / 文章」；补齐作者、统计字段。

---

### 🔴 缺陷 3：评论系统双轨（`evaluations` + `post_reply`）

| evaluations (10行) | post_reply (0行) |
|---|---|
| `content_type` + `content_id`（**多态**，可评论任意内容） | `post_id`（**专用**，只能评论帖子） |
| `parent_id`（树形） | `parent_id` |
| `upvote_list` | `like_count` |

`evaluations` 的多态设计是**正确的**，但 `post_reply` 又建了一套专用表。

**处置**：统一为 `comment` 表，保留多态设计，`post_reply` 数据并入。

---

### 🴠 缺陷 4：消息系统双轨（`message` + `notification`）

`message` 字段命名混乱：`content` / `user_id` / `send_id` / `replier_id` / `is_read` / **`other`（含义不明）**
`notification` 结构规范：`user_id` / `title` / `content` / `type` / `is_read`

**处置**：统一为 `notification`，`message` 数据并入，`other` 字段语义待定（需查代码确认是"对方用户"还是"其他数据"）。

---

### 🔴 缺陷 5：健康指标双存储（`patient_profile` 26 字段 vs `user_health` 表）

**这是最严重的一处。** `patient_profile` 把 8 个具体指标**硬编码成字段**：
```
fasting_blood_glucose, postprandial_blood_glucose,
total_cholesterol, triglycerides, hdl_cholesterol, ldl_cholesterol,
systolic_pressure, diastolic_pressure, resting_heart_rate
```
而 `user_health` 用标准 EAV 模式存**同一批指标**：`user_id + health_model_config_id + value`。

**实测数据自相矛盾**（user_id=2）：
```
patient_profile.systolic_pressure = 128
user_health 收缩压 = 124.0 / 125.2 / 126.4   ← 三个值，与上面都对不上
```

**附带问题**：`health_model_config` 字典只有 5 个指标（收缩压/舒张压/空腹血糖/体重指数/心率），
**覆盖不了 `patient_profile` 里那 8 个字段**——血脂四项、餐后血糖在字典里根本不存在，无法纳入趋势分析。

**处置**：
1. 指标值**只存 `user_health`**，删除 `patient_profile` 的 9 个指标字段
2. 补全 `health_model_config` 字典（血脂四项、餐后血糖、身高、体重等）
3. `patient_profile` 只保留人口学与生活方式字段（gender/age/birth_date/height/weight/bmi/病史/过敏史等）

---

### 🟡 缺陷 6：`appointment` 三重冗余

```
appointment(patient_id, doctor_id, schedule_id, department_id, appointment_date, time_slot, ...)
                          ↑           ↑             ↑
                    可由doctor推出  schedule里已有   可由doctor推出
```
`doctor_schedule` 已含 `doctor_id` + `schedule_date` + `time_slot`，`appointment` 又抄了一遍。

> **注意**：这属于**有意识的反范式**（避免多表 JOIN，查询更快）。**不建议删除**，但要加约束保证一致性。

---

### 🟡 缺陷 7：`health_model_config` 语义混乱

```
health_model_config(id, user_id, name, ..., is_global, category)
                                   ↑        ↑         ↑
                             is_global=1 时 user_id 存 0
                             is_global 与 category(PUBLIC/PERSONALIZED) 语义重叠
```
用 `is_global` 布尔位区分"系统字典"与"用户自定义"是脆弱设计。

**处置**：拆为 `health_indicator`（系统指标字典，不可删）+ 用户自定义另表，或统一加 `owner_type` 规范化。

---

### 🟡 缺陷 8：`quiz_record` 汇总字段冗余

`score` / `total_score` / `correct_count` / `question_count` 均可由 `quiz_answer` 汇总得出。

> 这同样属于**合理的反范式**（列表页免 JOIN，直接读汇总值）。**建议保留**，但要在写入时保证与明细一致。

---

### 🟡 缺陷 9：零外键约束

**383 个字段，0 个 FOREIGN KEY。** 所有关联（`user_id`/`doctor_id`/`post_id`…）全靠应用层维护。

**后果**：
- 删用户不会级联，遗留孤儿记录
- 字段改名/表合并时无法批量校验影响面
- 数据一致性只能靠代码自觉

---

### 🟡 缺陷 10：`hospital_doctor.user_id` 双重身份

`hospital_doctor` 有 `user_id` 字段 —— 意味着**医生同时是一条 `user` 记录**。
这会导致：改一次医生资料要同步两表；医生登录后 `user.role` 该填什么？

**处置**：明确医生身份策略（见第四节）。

-- ========== 统一内容表（合并 news + post）==========
CREATE TABLE content (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  content_type  VARCHAR(20)  NOT NULL COMMENT 'NEWS资讯 / POST帖子 / ARTICLE文章',
  user_id       INT UNSIGNED           COMMENT '作者，资讯可空',
  title         VARCHAR(200) NOT NULL,
  summary       VARCHAR(500)          COMMENT '摘要/导读',
  content       LONGTEXT,
  cover         VARCHAR(255)          COMMENT '封面图 URL',
  tag_id        INT UNSIGNED,
  -- 统计（合并 post 的字段；news.reader_ids 改为按 user_id 查阅读记录）
  view_count    INT DEFAULT 0,
  like_count    INT DEFAULT 0,
  favorite_count INT DEFAULT 0,
  comment_count INT DEFAULT 0,
  view_count_readers JSON               COMMENT '保留兼容，迁移后可删',
  hot_score     DECIMAL(10,4) DEFAULT 0,
  status        TINYINT DEFAULT 1 COMMENT '0草稿 1发布 2下架',
  is_top        TINYINT DEFAULT 0,
  is_banner     TINYINT DEFAULT 0 COMMENT '是否进首页轮播（news 专有）',
  published_at  DATETIME,
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_type_status (content_type, status, published_at DESC),
  KEY idx_user (user_id),
  KEY idx_tag (tag_id),
  CONSTRAINT fk_content_user FOREIGN KEY (user_id) REFERENCES user(id) ON DELETE SET NULL,
  CONSTRAINT fk_content_tag  FOREIGN KEY (tag_id)  REFERENCES tags(id)  ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='统一内容表（资讯/帖子/文章）';

-- ========== 统一标签表（合并 tags + post_tag）==========
-- sort_order 来自 post_tag，type 区分用途
ALTER TABLE tags
  ADD COLUMN sort_order INT DEFAULT 0 COMMENT '排序权重',
  ADD COLUMN type       VARCHAR(20) DEFAULT 'GENERAL' COMMENT 'GENERAL通用 / POST论坛 / NEWS资讯',
  ADD COLUMN status     TINYINT DEFAULT 1,
  ADD UNIQUE KEY uk_tag_name_type (name, type);

-- ========== 统一评论表（合并 evaluations + post_reply）==========
CREATE TABLE comment (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  target_type   VARCHAR(20) NOT NULL COMMENT 'CONTENT内容 / QUIZ题目 / NEWS资讯',
  target_id     BIGINT UNSIGNED NOT NULL COMMENT '多态目标 ID',
  user_id       INT UNSIGNED NOT NULL COMMENT '评论人',
  reply_to_id   BIGINT UNSIGNED          COMMENT '被评论人（evaluations.replier_id）',
  parent_id     BIGINT UNSIGNED          COMMENT '树形父评论',
  content       TEXT NOT NULL,
  like_count    INT DEFAULT 0,
  upvote_list   JSON                    COMMENT '兼容 evaluations.upvote_list',
  status        TINYINT DEFAULT 1,
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_target (target_type, target_id, status),
  KEY idx_parent (parent_id),
  CONSTRAINT fk_comment_user FOREIGN KEY (user_id) REFERENCES user(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='统一评论表（多态）';

-- ========== 科室表扩展：层级 + 编码 ===========
ALTER TABLE department
  ADD COLUMN parent_id  INT UNSIGNED DEFAULT 0 COMMENT '父科室，0=顶级',
  ADD COLUMN code       VARCHAR(30)                COMMENT '科室编码 如 CARDIO',
  ADD COLUMN leader_id  INT UNSIGNED               COMMENT '科主任（hospital_doctor.id）',
  ADD COLUMN level      TINYINT DEFAULT 1,
  ADD UNIQUE KEY uk_dept_code (code),
  ADD KEY idx_parent (parent_id),

-- ========== 医生表扩展：多科室 + 职称枚举 ===========
ALTER TABLE hospital_doctor

  ADD COLUMN specialties   JSON         COMMENT '擅长领域标签数组',
  MODIFY COLUMN expertise  TEXT         COMMENT '擅长描述（原字段）',
  ADD COLUMN visit_count   INT DEFAULT 0,
  ADD COLUMN rating        DECIMAL(3,2) DEFAULT 5.00;

### 2.3 数据迁移脚本要点

```sql
-- ① 内容合并
INSERT INTO content (content_type, user_id, title, content, cover, tag_id,
                     view_count_readers, is_top, is_banner, created_at)
SELECT 'NEWS', NULL, name, content, cover, tag_id,
       reader_ids, is_top, is_banner, create_time
FROM news;

INSERT INTO content (content_type, user_id, title, content, cover, tag_id,
                     view_count, like_count, favorite_count, comment_count,
                     hot_score, status, is_top, created_at, updated_at)
SELECT 'POST', user_id, title, content, cover, tag_id,
       view_count, like_count, favorite_count, comment_count,
       hot_score, status, is_top, create_time, update_time
FROM post;

-- ② 标签合并（去重：用 name 做唯一键，post_tag 的独有标签插入 tags）
INSERT IGNORE INTO tags (name, type, sort_order, created_at)
SELECT name, 'POST', sort_order, create_time FROM post_tag;

-- ③ 评论合并（post_reply → comment；evaluations → comment）
INSERT INTO comment (target_type, target_id, user_id, parent_id, content, like_count, created_at)
SELECT 'CONTENT', post_id, user_id, parent_id, content, like_count, create_time
FROM post_reply;

-- ④ 指标回填：patient_profile 的硬编码字段 → user_health
INSERT INTO user_health (user_id, health_model_config_id, value, created_at)
SELECT p.user_id, c.id, p.fasting_blood_glucose, NOW()
FROM patient_profile p JOIN health_model_config c ON c.name='空腹血糖'
WHERE p.fasting_blood_glucose IS NOT NULL;
-- ... 其余 8 个指标同理（需先补全字典）

-- ⑤ 灰度期：保留旧表只读，新表双写，验证通过后再 DROP
```

> ⚠️ **强烈建议采用灰度切换**：迁移期新旧表双写 → 校验一致 → 停双写 → 改名归档 → 最终删除。
> 不要一步到位 DROP，当前所有表都无外键，一旦删错无法回滚。

## 三、数据质量与工程约束

| 约束 | 规则 |
|------|------|
| **建表规范** | 新建表前**必须**先查 `information_schema` 确认无同类表；实体命名 `名词复数`，关联字段统一 `<目标表单数>_id` |
| **外键** | 核心业务表（user/content/comment/department/hospital_doctor/appointment）**必须加 FOREIGN KEY** |
| **软删** | 所有业务表统一 `status` 字段，不物理删除 |
| **时间字段** | 统一 `created_at` / `updated_at`，废弃 `create_time` / `update_time` 混用 |
| **注释** | 每张表、每个字段**必须有中文 COMMENT**（当前 `model_announcement`、`ai_usage` 注释乱码） |
| **字符集** | 统一 `utf8mb4` / `utf8mb4_general_ci`（当前 `user` 表为 `utf8mb4_bin`，排序会异常） |

**字符集不一致是隐患**：`user` 表用 `utf8mb4_bin`（二进制排序，区分大小写），其他表是 `utf8mb4_general_ci`。用户名字典序排序会不一致。

## ⚠️ 实施过程中修正的错误与踩过的坑

### 🔴 纠正：字符集问题比早期报告描述的小得多
**早期审计报告称「`user` 表是 `utf8mb4_bin`，排序会异常」——经 `information_schema` 逐列核实，这是误判。**

实际情况：
- 全库 42 张表中 **41 张是 `utf8mb4_0900_ai_ci`**（含 `user` 全部字段，排序完全正常）
- 真正遗留 MySQL 5.7 旧规则的**只有 `model_announcement` 的 6 个字段**（`utf8mb4_unicode_ci`）

因此统一目标改为 `utf8mb4_0900_ai_ci`（不是 `general_ci`——后者是 5.7 老旧规则，改过去反而是降级），且**只需改 1 张表**。

### 坑 1：MySQL 不支持 `ADD COLUMN IF NOT EXISTS`
那是 MariaDB 语法。MySQL 9.7 同样不支持，脚本改用 `SET @d = IF(EXISTS(...),'DO 0','ALTER...') + PREPARE/EXECUTE` 实现幂等。

### 坑 2：存储过程传中文参数会乱码
最初用存储过程封装幂等逻辑，结果 COMMENT 中文变成 `帖å­`。
实测验证后改用 **`SET` 变量 + PREPARE**（DDL 直接写 SQL 字面量），中文完全正常。
> 结论：MySQL 脚本里**不要用存储过程参数传递中文**。

### 坑 3：用户密码是 BCrypt，不是 MD5
`user` 表密码格式为 `$2a$10$...`（BCrypt），后端用 `PasswordEncoder`。
且**本实例 `MD5()` 函数不可用**（报 `FUNCTION MD5 does not exist`），而 BCrypt 哈希 SQL 无法生成。
→ 因此脚本**不写死医生初始密码**，改为：
  - `password = NULL` + 新增字段 `need_init_password = 1`
  - 医生首次登录时强制设置初始密码；管理员也可在管理端随时重置

### 坑 4：`LPAD(id, 3, '0')` 会截断 4 位 id
医生 id 实际是 **3001/3002/3003**（`TABLE_ROWS` 估算值显示 3 是 InnoDB 估算不准，容易误判）。
`LPAD(3001, 3, '0')` 返回 `'300'`（**截断而非补零**），导致三行 username 全部撞成 `doctor300`，唯一索引构建失败。
→ 账号规则改为 `CONCAT('doctor', id)`，得 doctor3001 / doctor3002 / doctor3003。

### 坑 5：`notification.type` 是 tinyint 不是 varchar
误按字符串写入 `'MESSAGE'` 报 `Incorrect integer value`。
实际枚举：0系统公告 1预约通知 2随访通知 3订单通知 **4私信消息**。

### 坑 6：`information_schema.TABLES.TABLE_ROWS` 是估算值
InnoDB 下不准确，审计时用它判断"表有 3 行"是误导，实际查询 `COUNT(*)` 才知道真实数据。**涉及数据量的判断必须用 `COUNT(*)`。**

### 缺陷 6 的判断修正（重要）

初版判定「`patient_profile.systolic_pressure=128` 与 `user_health` 的 124/125.2/126.4 数据打架」，
**实测证明这是误判**：

- `patient_profile.systolic_pressure` = **最近一次的快照**（医生看诊时的当前值）
- `user_health` 的三个值 = **三次不同日期的测量序列**（用于趋势分析）

两者语义不同，**不构成冲突**。真正的设计问题是「同一指标存两处、来源不统一」，
而非「数值对不上」。

处置：**未删除 `patient_profile` 的 9 个指标字段**，理由：
1. 医生端「患者详情」需要一屏看到当前血压/血糖/血脂，EAV 查询要多表 JOIN 多次
2. 快照与序列各有用途，强行合一反而丢语义
3. 指标字典已从 5 个补到 **12 个**（含血脂四项、餐后血糖），
   初版「字典覆盖不全」的问题已解决

若未来确需单源，建议做法：保留 `patient_profile` 作为**缓存快照**，
写入时同步更新 `user_health`（以 `user_health` 为准），而非删除快照字段。
