## 一、Redis 迁移 Docker —— 可行，且基础设施已就绪

### 现状（好消息）

`docker-compose.yml` **早已定义了完整的 Redis 服务**（第 79-93 行）：

```yaml
redis:
  image: redis:7-alpine
  container_name: zhikangyun-redis
  restart: unless-stopped          # ← 重启电脑自动拉起
  command: ["redis-server", "--appendonly", "yes"]   # ← AOF 持久化
  volumes: [redis_data:/data]      # ← 数据卷持久化
  healthcheck: ["CMD", "redis-cli", "ping"]
```

后端 `backend` 服务也已经 `depends_on: redis: condition: service_healthy`，`REDIS_HOST: redis` 也配好了。

**所以你不需要新增任何配置，只需要把它跑起来。**

### 遇到的真实障碍（已定位）

1. **Docker Desktop 引擎没启动**（Compose v5.1.3 已安装，但 `dockerDesktopLinuxEngine` 管道不存在）
2. **缺 `.env` 文件** —— compose 里有 4 个强制变量：  
   `DB_ROOT_PASSWORD` / `JWT_SECRET` / `CRM_API_KEY` / `GRAFANA_ADMIN_PASSWORD`  
   用 `${VAR:?提示}` 语法，**缺失时 compose 会在"解析阶段"直接失败**——即使你只想 `up redis` 也一样
3. **`.env.example` 本身就缺 `CRM_API_KEY` 和 `GRAFANA_ADMIN_PASSWORD`**  
   → 意味着**任何人照着 `.env.example` 配都起不来 compose**。✅ 已修复（补齐了这两个变量和 Redis 段）

### 三个可选方案

**方案 A：全容器化（生产一致，推荐）**

```bash
# 1. 启动 Docker Desktop
# 2. 准备环境变量
cp .env.example .env    # 然后把里面的占位符换成真实值
# 3. 起全套
docker compose up -d
```

**方案 B：只把 Redis 放进 Docker（本地开发最轻量，MySQL 和后端仍在本机）**

```bash
# 需要先 cp .env.example .env 填好 4 个必填变量（否则解析失败）
docker compose up -d redis
```

此时后端连 `localhost:6379`（compose 已把 6379 端口映射到宿主机），MySQL 仍连本机 3306。

**方案 C：完全绕开 compose（最省事，零配置）**

```bash
docker run -d --name zhikangyun-redis-dev \
  -p 6379:6379 \
  -v zhikangyun-redis-dev:/data \
  redis:7-alpine redis-server --appendonly yes
```

**这是你现在最该用的**——不碰 compose、不需要 .env、一条命令解决"重启电脑 Redis 就没了"的问题。

### 需要注意的坑

- **端口冲突**：本机的 `redis-server.exe`（PID 32656，我刚启动的）也占 6379。进 Docker 前要先 `taskkill` 掉它
- **数据迁移**：本机 Redis 在 `D:\Program Files\Redis\dump.rdb`（含 `auth:user:*:ver` 会话版本）。换到 Docker 后这些键会丢，**所有用户需要重新登录一次**（因为版本号从 0 开始）——这其实是好事，清理了累积 35 次的脏版本
- `restart: unless-stopped` 只在 Docker Desktop 开机自启的前提下生效

## 三、行业对标：WiseClaw 有什么值得学

### WiseClaw 是什么

智诊科技（WiseDiag）推出的**医疗行业 AI Agent Operating System**，基于 OpenClaw 架构。协和、北大、交大、浙大等已申请内测。定价：专业版 12999/年。

### 核心架构：「Agent + Skill」

它把医疗大模型封装成**可组装、可复用**的智能体服务，用**三层 Skill 体系**驱动（官方预设 Skill → 第三方市场 → 自然语言自建 Skill），像"应用商店"一样管理医疗 AI 能力。

### 四个最值得借鉴的点

#### ① Agent 与 Skill 分层解耦（★最高优先级）

**它怎么做**：Agent 是"编排与决策层"，Skill 是"原子能力层"。新增能力 = 新增一个 Skill，**不改 Agent 主流程**。

**本项目现状**：`SystemConfigManage.vue` 2234 行把所有配置（系统参数/LLM/模型/智能体/ASR/TTS/VAD 七类）塞在一个巨型组件里；`AiDoctorManage.vue` 与它逻辑重复。**这是"单体大组件"模式，天花板极低。**

**可借鉴的改造**：

- 参照它的 Skill 分层，把 `AiPromptConfig` 的 `PresetConfig` 升级为独立的 **Skill 定义**（名称、描述、入参 schema、执行体、知识库绑定、风险等级）
- 智能体 = Skill 列表的编排，而非一个大 Prompt
- 立刻可做的轻量版：把 `SystemConfigManage.vue` 按 7 个 Tab 拆成子组件（纯重构，零风险）

#### ② 医学证据链：每条输出可追溯（★医疗场景刚需）

**它怎么做**：内置"医学证据链"机制，确保每一条 AI 输出可追溯到具体依据；配合"可审核资料 + 禁答规则 + 测试记录"，把上线前确认动作前置。

**本项目现状**：`AiHealthDataServiceImpl` 有个严重的**可信度问题**——把解析失败伪装成 `status: "unknown"`。AI 拿到"指标未知"会给用户错误解读，**这在医疗场景是数据可信度事故**。

**可借鉴的改造**：

- AI 回答附带**引用来源**（哪篇资讯/哪条知识库/哪项健康数据）
- 解析失败要明确区分 `invalid`（脏数据，需告警）而非 `unknown`
- 增加"禁答清单"：诊断类问题（"我是不是XX病"）统一走免责话术 + 引导线下就医

#### ③ 跨会话/跨周期的持久化健康记忆

**它怎么做**：Harness 架构建立动态健康档案，跨会话持久化，复诊"秒级认知病史"。

**本项目现状**：`AiChatCacheServiceImpl` 的 `messageCache` / `conversationCache` 是**纯内存 Map，无上限无 TTL**，且定时清理从未运行（见第四节）→ 进程一重启记忆全丢，还可能 OOM。

**可借鉴**：记忆持久化到 MySQL/文件 + LRU 上限，而不是堆内存。

#### ④ Workspace 多租户物理隔离

**它怎么做**：企业级 Workspace 隔离，多租户架构，数据/记忆/权限物理与逻辑隔离，满足医疗级合规。

**本项目现状**：单租户，权限只判断 `token != null`，**无角色级路由守卫**（`router/index.js:270`），`userRole` 只控制跳 `/admin` 还是 `/user`，前端菜单不按角色收敛。

**可借鉴**：如果未来要支持多家医院/体检中心，这是必做项。

### 差距总结

| 维度          | WiseClaw            | 本项目                 | 差距    |
| ----------- | ------------------- | ------------------- | ----- |
| 能力组织        | Agent + Skill 三层体系  | 单体大组件 + 散落配置        | **大** |
| 记忆          | 跨周期持久化档案            | 内存 Map（易失 + OOM 风险） | **大** |
| 可追溯         | 医学证据链               | 无                   | **大** |
| 治理          | Workspace 隔离 + 评测审计 | 单一角色判断              | **中** |
| 自然语言建 Skill | 支持向导式生成             | 无（纯表单配置）            | **中** |

**务实建议**：不要一上来抄整套。先做「Skill 定义化 + 智能体编排」这一件事——它同时解决了可维护性、扩展性和与行业接轨三个问题。

## 四、异步管理与代码缺陷审查

### 后端评分：**68 / 100**

> 结论：安全底线和资源生命周期做得比一般项目好（JWT fail-closed、OkHttp 全部单例复用、`${}` 注入零 SQL 注入），但**异步基础设施整体缺失**。

### P0：定时任务从未运行过（隐蔽故障）

`PersonalHealthApplication.java:9-11` 只有 `@SpringBootApplication`，**全项目 grep 无 `@EnableAsync`、无 `@EnableScheduling`**。

而 `HotScoreServiceImpl` 声明了 `@Scheduled(fixedRate=3600000)` —— **该注解完全不生效，帖子热度分从未被定时刷新过**，只能靠单点触发。

> 这是"看起来有、实际没跑"的最高危类型，因为没有任何报错。

**修复**：启动类加 `@EnableScheduling`，改完立即验证热度分是否开始更新。

### P0：4 处明文密钥入库

| 位置                      | 内容                            |
| ----------------------- | ----------------------------- |
| `application.yml:22-23` | MySQL `root` / `1234`         |
| `application.yml:66`    | 硅基流动 API Key `sk-wkmdanxb...` |
| `application.yml:76`    | JWT secret                    |
| `application.yml:82`    | Neo4j password `12345678`     |

**建议按"已泄露"处理，立即轮换**，全部改为 `${ENV_VAR}` 占位（`application-prod.yml` 已有正确写法可参考）。

### P1 清单（择要）

| 位置                                                          | 问题                                                                                                                               |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `AiChatCacheServiceImpl:36-37`                              | 两个 `ConcurrentHashMap` **无上限、无淘汰、无 TTL** + 定时清理从未运行 = **确定的 OOM**                                                                |
| `TTSFactory:79`、`EdgeTTSProvider:129`、`VoiceServiceImpl:59` | 3 处 `CompletableFuture.supplyAsync` **未传 Executor**，落到 `ForkJoinPool.commonPool()`，而任务是**阻塞式网络调用**（数秒）→ 高并发时会占满并阻塞其他 ForkJoin 任务 |
| `core/async/TaskQueue.java`                                 | 0 引用死代码 + `newFixedThreadPool(10)` 无界队列 + **无 `@PreDestroy`** → 线程泄漏                                                             |
| `HotScoreServiceImpl:33-36`                                 | **N+1 查询**：全量捞帖子后循环里逐条 UPDATE，上万帖子 = 上万次单条写                                                                                      |
| `ModelAnnouncementServiceImpl:51,63,75,87`                  | 连续 4 个方法 `catch → return false`，公告增删改查**全部静默失败**                                                                                 |
| `AiChatCacheServiceImpl:211,214,217`                        | `persistToFile(){}` 空实现、`loadFromFile(){return false}`、`restoreAllFromJson(){return emptyMap}` —— 类注释宣称的"JSON 备份链路"**根本不存在**     |
| `UserServiceImpl:278`                                       | `// TODO: 实现用户设置持久化` → 用户设置**保存静默无效**，前端以为成功了                                                                                    |
| `Neo4jClient:41-47`                                         | 连接失败只 `log.warn` 留 `driver=null`，应用照常启动，图谱查询静默返回空 → `neo4j.enabled: true` 形同虚设                                                   |

**好消息**：SQL 注入 **0 处**（全项目 mapper XML 中 `${` 出现 0 次）；`batchDelete` 正确使用 `<foreach>` 真批量；文件写入用了 `ATOMIC_MOVE`；WebSocket 用 `SESSIONS.remove(k,v)` 双参删除避免误删。

### 死代码清理清单

- `core/voice/AudioManager.java`、`core/voice/VADDetector.java` —— 0 引用
- `core/async/TaskQueue.java` —— 0 引用
- `TTSFactory` 的 `cosyvoice` / `minimax` 分支是 TODO 占位，**选了却回退到 EdgeTTS**，前端无提示
- 3 处 TTS 合成逻辑重复（`synthesize` + `synthesizeAsync`），改一处必漏另两处
- 4 个重叠工厂类：`LLMFactory` vs `LLMProviderFactory`、`ASRFactory` vs `TTSFactory`

### 建议修复顺序（Top 5）

1. 补 `@EnableScheduling`（1 行，热度分立刻生效）
2. 轮换并移除 4 处明文凭据
3. 给两个无界缓存加上限（防 OOM）
4. 3 处 `supplyAsync` 指定专用线程池 + 删 `TaskQueue`
5. 清理 6 处"空实现/静默失败"（共同危害是**故障静默化**）

### 必须加的三道护栏（医疗合规）

1. **免责声明**：所有 AI 生成图片显著标注"AI 生成，仅供参考，不构成医疗建议"
2. **人工审核流**：生成图进入草稿态，管理员审核后才发布（复用现有 `ContentAuditService` 内容审核机制）
3. **提示词护栏**：后端过滤敏感词，禁止生成"病灶示意/诊断图像"这类可能误导的医疗内容——**AI 生图不能用于任何诊断性影像**

### 技术接入建议

- 复用现有 `LLMFactory` 的工厂模式，新建 `ImageFactory` + `ImageProvider`，与 `ASRFactory`/`TTSFactory` 保持一致
- 配置项加入 `VoiceConfigHolder` 同款动态配置（`ImageConfigHolder`），持久化到 `./config/image-config.json`
- **复用现有的文件上传链路**（`FileController` + `FILE_STORAGE_ROOT` 持久化卷），生成图落到 `/file/getFile` 可访问路径
- ⚠️ **注意网络可达性**：和 Edge TTS 一样的问题——服务端必须能出网到对应域名。建议接入前先加一个 `/image/test` 自测端点（参照这次做的 `/voice/test`）
